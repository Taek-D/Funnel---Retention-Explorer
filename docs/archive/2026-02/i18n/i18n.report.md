## 7. Lessons Learned & Retrospective

### 7.1 What Went Well (Keep)

1. **Comprehensive design documentation** — The i18n.design.md provided clear specifications for all 6 subtasks (I18N-1 through I18N-6), making implementation straightforward and reducing ambiguity.

2. **Namespace separation strategy** — Using 3 namespaces (common, pages, insights) keeps translation files organized and maintainable. This made it easy to locate and update strings across different parts of the app.

3. **Zero-iteration first-pass** — The implementation achieved 92.9% match on the first pass, demonstrating good planning and design discipline. Only 2 optional SEO features were deferred (document.title and hreflang).

4. **Test infrastructure planning** — Mocking react-i18next in setupTests.ts upfront prevented breakage of all 208 existing tests, which would have been time-consuming to fix individually.

5. **Locale detection strategy** — Using localStorage + navigator fallback ensures users' language choice persists across sessions while respecting browser language preferences.

6. **Key naming conventions** — Using dot notation (nav.dashboard, plan.pro) makes keys intuitive and self-documenting, reducing translation key lookup overhead.

### 7.2 What Needs Improvement (Problem)

1. **SEO features partially deferred** — Document title i18n and hreflang links were identified as gaps but not implemented. While not critical for MVP, these should have been prioritized higher given they were in the design spec (I18N-6).

2. **formatNum() locale awareness missing** — The formatters.ts module only partially uses i18n.language; formatNum() still defaults to browser locale, which may not match user's selected language.

3. **csvParser.ts error messages remain untranslated** — Despite being listed in the design scope, CSV parser errors remain hardcoded in Korean. The user-facing layer (useCSVUpload) does translate messages, creating inconsistency in error handling.

4. **Sidebar button ordering** — LanguageSwitcher placement differs from design (after PlanBadge instead of before). While functionally correct, this is a minor UX inconsistency.

### 7.3 What to Try Next (Try)

1. **Automated translation validation** — Implement a build-time check that ko/* and en/* JSON files have identical key structures. This would catch missing translations immediately rather than at runtime.

2. **Translation key audit tool** — Create a utility that scans all `.tsx` and `.ts` files to identify hardcoded strings not yet extracted to locale JSON files. This would prevent accidental regression.

3. **Locale-aware formatting library** — Consider adopting date-fns/dayjs with i18n support instead of Intl API for more robust locale handling (e.g., relative time formatting like "2 hours ago").

4. **Dynamic page titles by route** — Implement a route-aware title update that changes `document.title` based on current page and language (e.g., "Dashboard - FRE Analytics" in English, "대시보드 - FRE Analytics" in Korean).

5. **Crowdsourced translation workflow** — If expanding to more languages in the future, establish a process for community translations (Crowdin, Lokalise) rather than manual JSON editing.

## 9. Technical Implementation Highlights

### 9.1 Architecture Pattern

```
┌─────────────────────────────────────────────────┐
│ index.tsx (import './lib/i18n')                 │
├─────────────────────────────────────────────────┤
│ lib/i18n.ts (i18next + detection + event)      │
│  - Namespace: common, pages, insights           │
│  - Detection: localStorage, navigator           │
│  - Fallback: 'ko'                               │
├─────────────────────────────────────────────────┤
│ Components / Pages / Hooks                      │
│  - useTranslation('namespace')                  │
│  - const { t, i18n } = useTranslation(...)     │
│  - t('key.subkey', { var: value })             │
├─────────────────────────────────────────────────┤
│ Lib modules (non-React)                         │
│  - import i18n from './i18n'                    │
│  - i18n.t('namespace:key', { vars })           │
├─────────────────────────────────────────────────┤
│ locales/ko | locales/en                         │
│  - common.json (~175 keys)                      │
│  - pages.json (~285 keys)                       │
│  - insights.json (~85 keys)                     │
└─────────────────────────────────────────────────┘
```

### 9.3 Component Modification Pattern

**React Components** (useTranslation hook):
```tsx
import { useTranslation } from 'react-i18next';

export const MyComponent: React.FC = () => {
  const { t, i18n } = useTranslation();
  // or: const { t } = useTranslation('pages');
  return <span>{t('nav.dashboard')}</span>;
};
```

**Class Components** (import i18n directly):
```tsx
import i18n from '../lib/i18n';

export class ErrorBoundary extends Component {
  render() {
    return <span>{i18n.t('error.title')}</span>;
  }
}
```

**Non-React Lib/Hooks**:
```typescript
import i18n from '../lib/i18n';

export function processData() {
  toast('success', i18n.t('insights:toast.processComplete'));
}
```
